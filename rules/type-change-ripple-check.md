# Type Change Ripple Check (타입 변경 파급 검토)

여러 곳에서 공유하는 타입·인터페이스·데이터 구조(요청 바디로 그대로 나가는 객체, 여러 컴포넌트/앱이
소비하는 공용 타입 등)에 필드를 추가·변경하기 전에 **그 구조가 실제로 어떻게 소비되는지** 추적한다.
"타입만 넓히면 안전하다"는 가정으로 코드를 작성하지 않는다.

## When (alwaysApply — 코드 작성/제안 시 항상 적용)

- 여러 파일·앱이 import하는 공용 타입(`interface`, `type`)에 필드 추가
- 검증·디버깅용 임시 필드를 프로덕션 데이터 구조에 얹는 설계
- `...spread`로 객체를 그대로 API body/외부 시스템에 전달하는 코드 근처에서 그 객체의 필드를 바꿀 때

해당 없음: 로컬 함수 내부에만 쓰이는 타입, 이미 화이트리스트 방식(필드를 하나씩 destructure해서 보내는)으로
전송하는 구조.

## Contract (MUST)

새 필드를 공용 타입에 추가하기 전에 다음을 **grep으로 직접 확인**한다 — 추정으로 넘어가지 않는다.

1. **직렬화 경로 확인**: 이 객체(또는 이 타입의 배열)가 API 호출부에서 `JSON.stringify` 또는 `body: {...obj}`
   형태로 **통째로 전송되는지** 확인한다. 화이트리스트(개별 필드 destructure)면 새 필드는 자동으로 걸러지지만,
   스프레드/배열 그대로 전송이면 새 필드가 서버로 그대로 나간다.
   ```bash
   grep -rn "{TYPE_NAME}" --include="*.ts" --include="*.tsx" .
   grep -rn "\.\.\.{변수명}\|{변수명}\s*[,}]" api호출부파일
   ```
2. **소비자 전체 나열**: 같은 타입을 쓰는 모든 파일을 grep해 나열한다. 멀티 앱 구조(예: amazon/luxury/pdp/retail
   처럼 같은 패턴이 앱마다 복제된 코드)면 **앱 개수만큼** 확인 지점이 있다는 것을 전제한다.
3. **검증용 필드는 전송 전 제거를 별도 단계로 명시**하고, 그 제거 코드가 **모든 전송 경로**(예: 장바구니 담기·
   즉시구매·선물하기처럼 같은 데이터를 쓰는 여러 액션)에 빠짐없이 들어가는지 확인한다. 하나라도 빠뜨리면
   그 경로만 조용히 깨진다.
4. **서버 계약이 strict인지 실측하지 않았다면 "무해하다"고 단정하지 않는다.** unknown 필드를 무시하는 서버도
   있고 거부하는 서버도 있다 — 실측 없이 "아마 무시할 것"으로 넘어가지 않는다. 실측이 어려우면(운영 API
   승인 필요 등) 애초에 공용 타입에 필드를 얹지 않는 대안(검증 로직을 데이터 구조 밖에서 독립 수행)을 우선한다.

## 대안 우선순위 (필드 추가보다 선호)

검증·디버깅 목적이라면, 공용 타입에 필드를 얹는 대신 아래를 먼저 고려한다.

- 검증 로직을 별도 함수/훅으로 분리해 원본 데이터 구조를 건드리지 않고 독립적으로 재계산
- 이미 있는 사이드 채널(로깅 유틸, Sentry breadcrumb 등)로 상태를 남기고 데이터 구조는 그대로 둠

## 실패 사례

PDP MW `useOrderParameters`/`useCouponPrice`의 `countMap` 동기화 방어 검토 중, "무효 상태를 표시하는
`isCountMapMissing` 필드를 `OrderParametersForRequest`에 추가"하는 방안이 나왔다. 이 타입의 배열은
`postAcmeCart`/`postAcmeOrder`에서 `products: orderParameters`로 **화이트리스트 없이 그대로 전송**되고,
`onClickCart`/`onClickOrder`/`onClickGift` **3개 경로** 각각에서 필드를 제거해야 했다. 하나라도 놓치면
매 정상 주문에 검증용 필드가 실려 나가고, 서버가 strict 스키마면 전체 주문이 깨질 수 있었다. 필드 추가
전 `grep`으로 전송 경로를 확인해 이 위험을 미리 잡았고, 검증 로직을 데이터 구조 밖으로 분리하는 방향으로
바꿨다.
