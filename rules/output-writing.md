# 에이전트 출력 작성 (PR·설명·요약)

PR 디스크립션·작업 요약을 **1차 초안부터 제출 가능**하게 쓴다. 톤 다듬기·목적 재해석을 위해 사용자가 여러 번 가공하게 두지 않는다.

## 적용 시점 (alwaysApply 아님)

**PR 디스크립션·PR 본문을 작성·수정할 때만** 이 룰을 Read하고 적용한다.

| 트리거 | 예 |
|--------|-----|
| PR 디스크립션 작성/수정 | "PR 설명 써줘", "디스크립션 만들어", "PR 본문 정리" |
| 팀 PR 형식 요청 | "기획/작업/리뷰기한 형식으로" |
| PR create/update 워크플로 | PR 생성·업데이트 직전 |

일반 코딩·디버깅·리뷰 응답에는 적용하지 않는다.

**전역(항상):** 목적 우선 → 팀 `purpose-over-mechanism` 룰(있을 때), 건조한 톤 → `communication-style`.

## 1. 목적 — 맞는 이유를 쓴다

- **실제 목적**을 먼저 쓴다. 그 작업의 1차 가치가 무엇인지 확인한 뒤 서술한다.
- 부수 효과(브랜치 동기화, SSOT, merge 편의)를 **주목적처럼** 쓰지 않는다.
- 판별: "이 문장만 읽었을 때, 팀/서비스가 얻는 것이 무엇인가?"

```markdown
# ❌ 부수 효과를 주목적처럼
마이그레이션 브랜치마다 설정이 갈라지면 불일치가 난다. master SSOT로 merge 후 SSR spec만 추가.

# ✅ 1차 목적
master에 E2E를 두어 5종 마켓 시나리오 커버리지를 확보한다. Next.js migration은 동일 targets로 SSR 검증에 쓴다.
```

## 2. 문장 — 짧고 건조하게

- 두괄식. 인사·완곡·감탄·"~하면 좋다" 류 패딩 금지.
- 같은 뜻이면 **짧은 표현**을 쓴다. 맥락상 충분하면 `E2E`, `targets`, `SSR`처럼 줄여 쓴다.
- 독자가 이미 아는 배경(왜 SSOT인지, 왜 env 분기인지)을 장문으로 반복하지 않는다.
- 사용자가 금지한 용어는 PR·요약 본문에 넣지 않는다. 코드 id·파일명 인용은 예외.

```markdown
# ❌ 장황·완곽
배포 전에 통합 PDP·리테일·럭셔리·아마존 5종 상품 시나리오를 상시 검증한다.

# ✅ 짧게
E2E로 통합 PDP·리테일·럭셔리·아마존 5종 시나리오 커버리지를 확보한다.
```

## 3. PR 디스크립션 형식

PR 본문은 아래 섹션만 사용한다. 다른 Summary/Changes 템플릿을 임의로 붙이지 않는다.

| 섹션 | 내용 |
|------|------|
| **기획 내용** | 왜 하는지(목적). Epic·티켓 한 줄 |
| **작업 내용** | 무엇을 바꿨는지. 파일·스크립트·표는 여기 |
| **리뷰기한** | 값 없으면 `-` |

- **기획 내용**: 2~3문장. migration·후속 작업은 1문장 이내 부가.
- **작업 내용**: 나열 위주. 표·명령어·파일 경로는 OK.
- 섹션 제목·순서 변경 금지.

## 4. 1차 초안 체크 (출력 전)

- [ ] 주목적이 이 PR/작업의 1차 가치와 일치하는가
- [ ] 부수 효과만 강조하지 않았는가
- [ ] 불필요한 형용사·완곽·친화 표현을 뺐는가
- [ ] 같은 정보를 두 문장 이상 반복하지 않았는가
- [ ] PR이면 기획/작업/리뷰기한(`-`) 형식인가

## 5. 사용자 수정 요청 시

"별로야", "목적이 달라", "legacy 빼" 등 피드백이 오면:

1. **문장만 바꾸지 말고** 잘못 잡은 목적·톤·용어를 먼저 수정한다.
2. 전체를 다시 쓸 때도 섹션 구조·분량을 유지한다.
3. "이 버전으로 갈까?"만 반복하지 않고, 수정 이유를 한 줄로 짚는다.
