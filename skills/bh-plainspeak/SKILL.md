# bh-plainspeak

구현 플랜 같은 기술 문서를 **말하듯 쉬운 구어체**로 풀어, **별도 md 파일**로 저장한다.
원문(기술 스펙)은 건드리지 않는다. "이게 대체 뭘 하겠다는 거지?"를 해소하는 것이 목적이다.

## 명령어

| 명령어 | 설명 |
|--------|------|
| `/bh-plainspeak [파일경로]` | 대상 md를 구어체 쉬운 설명 md로 변환해 별도 파일로 저장 |

## 스킬 유형
- **Encoded Preference**: 기술 문서를 쉬운 말 설명 문서로 따로 만들어 두는 사용자 선호.

## 핵심 원칙

1. **원문 보존** — 기술 md는 그대로 두고 **별도 파일**을 만든다. 기본 이름 `{원본basename}-쉬운설명.md`
   (또는 사용자 지정 위치, 예: `handoff/`). 원문 덮어쓰기 금지.
2. **전문용어 최소화, 쓰면 한 줄 풀이** — 불가피한 용어는 괄호로 뜻을 붙인다.
   예: `attendeeEmployeeIds` → "참석자 명단(사번)", `ownerUserId` → "그 녹음 트랙 주인",
   `401` → "로그인 안 됐으니 로그인 화면으로".
3. **정확성 유지** — 쉽게 쓰되 **사실을 바꾸지 않는다.** 수치·정책·상태 조건·순서는 원문과 일치해야 한다.
   쉬운 말로 바꾸다 조건을 뭉개면 안 된다(예: "SCHEDULED|RECORDING만" → "회의 중일 때만"은 OK,
   "아무 때나"는 왜곡).
4. **말하듯이, 두괄식, 담백하게** — "~할 거예요 / ~하는 거죠" 톤. 과장·칭찬·미사여구 금지
   (communication-style 준수).
5. **표·다이어그램은 말로 풀기** — 원문의 표/Mermaid를 그대로 복붙하지 말고 문장으로 설명한다.
   (다이어그램이 목적이면 `bh-create-workflow`를 쓴다.)

## 권장 구조 (대상이 구현 플랜일 때)

1. **한 줄 요약** — 결국 뭘 하는 건지 한 문장.
2. **지금은 이런 상태예요 (AS-IS)** — 왜 이걸 하는지.
3. **바꾸는 건 N가지예요** — 기능 단위로, 각 기능을 쉬운 말 + 예시로.
4. **어떤 순서로 하냐면** — 커밋/단계 순서.
5. **걱정 안 해도 되는 것** — DB 안 건드림, 위험 작업 없음 등 불변식.
6. **다 되면 이렇게 확인해요** — 인수 조건을 체크박스로.
7. 하단에 **원문(기술 상세) 링크**.

## 워크플로우

1. **대상 읽기** — 지정 파일(없으면 직전 맥락의 플랜/문서)을 읽는다.
2. **핵심 추출** — 목적, AS-IS/TO-BE, 기능 단위, 순서, 리스크·불변식, 인수 조건.
3. **용어 매핑** — 기술어 → 쉬운 말 대응을 먼저 정한다.
4. **초안 작성** — 위 권장 구조로 구어체 작성.
5. **사실 검증** — 원문과 수치·조건·상태를 대조해 왜곡이 없는지 확인한다.
6. **저장** — 별도 파일로 쓰고 원문 링크를 붙인다. 원문은 수정하지 않는다.
7. 저장 경로와 요약을 사용자에게 알린다.

## 금지

- 원문(기술 스펙) 덮어쓰기·삭제.
- 사실 변경 — 정책·수치·상태 조건·순서를 쉽게 쓴다는 이유로 왜곡.
- 과장·칭찬성 표현, 불필요한 이모지 남발.
- 표/Mermaid 원문 그대로 옮겨 "쉬운 설명"이라 부르기.
